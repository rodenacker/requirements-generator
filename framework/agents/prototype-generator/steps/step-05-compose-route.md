# step-05-compose-route

**Goal:** Assemble the **driver-owned** routes under `src/app/<name_slug>/**` and the shared intra-prototype nav, composing shared components into each coupled surface's realization. Standalone secondary surfaces authored their own route in their sub-agent (step-04 / `step-sub-render-surface.md`); the driver only **consumes** their route manifests here. Collision-free with sub-agents (the disjoint `owned_files` partition, step-02).

**Timing:** emit `substep_start` (`stage:"generator"`, `substep:"route-compose"`) before step 1 and `substep_end` after step 6, per `prototype-generator.md > Timing log (sub-steps)`.

For the prototype's surfaces (using the manifests from step-04 + reused components + the `route_map` from step-02):

1. **Who owns which route** (`route_map`, step-02; realization enum in `framework/assets/wireframes/realization-strategies.md`):
   - `standalone-screen` **secondary** (`is_parallelizable`) → **already authored by its sub-agent** (its `route_written` is in the manifest). The driver does **not** re-author it; it only confirms the surface→route mapping holds (every parallelizable surface returned a `route_written`; none missing — else route to retry/`RF-12` via step-06).
   - `standalone-screen` **primary/root** → driver authors `src/app/<name_slug>/page.tsx` (the cross-surface hub).
   - `inline-drawer` / `inline-expand` / `modal` → driver composes the fold into the **host** surface's route as a drawer/expandable/overlay sub-tree (the fold's components, from the host's manifest, rendered on the host page). Many-to-one → driver-owned.
   - `wizard-split` → driver authors a route with N sub-steps (stepper + per-step component); one route, staged disclosure.
2. **Shared intra-prototype nav.** When the spec's §6 navigation model needs nav spanning multiple standalone surfaces (sidebar / command-palette enumerating routes), the driver authors **one** per-prototype `src/app/<name_slug>/layout.tsx` carrying it, so every leaf page (driver- or sub-agent-authored) inherits it via Next.js nested layout — **no sub-agent writes shared nav**. When the model needs no shared per-prototype nav, omit the layout (pages self-wire back-link/breadcrumb; this is the `nav_context` the dispatch passed each standalone sub-agent). The app-level `layout.tsx` (inter-prototype chrome + `data-testid="proto-chrome"`) is scaffold-authored and untouched.
   - **App-shell obligations (colour-mode toggle + brand logo) — unconditional, topology-agnostic.** These two shared app-level affordances must be reachable from **every** prototype route. The obligation attaches to **whatever component wraps a surface's content**: the per-prototype `layout.tsx` when one carries the nav, **otherwise each** `templates/AppShell*` / `templates/*Shell` the surfaces compose. Any component that wraps a surface's content *is* an application shell for this rule — so a surface legitimately outside the main shell (a sign-in composing `templates/CenteredFormShell`) is covered by that shell, and "the shell" is never assumed to be a singleton. There is **no slot precondition and no topology test**: if the wrapping component has no app-level header region, **author one** (a slim strip above `main-content` suffices — it is UI-only chrome, not a catalogue slot).
     - Render them **inside** the shell component itself, never passed in as a prop by the page, so no page-level composer can omit them — and in an **app-level** header region, distinct from any page-level `title`/`breadcrumb`/`actions` prop the shell already accepts.
     - **Colour-mode toggle.** `import ThemeToggle from '@/components/atoms/ThemeToggle'` → `<ThemeToggle />`, **iff `prototypes/src/components/atoms/ThemeToggle.tsx` exists** (the scaffolder authors it exactly when `.scaffold.json` has `colour_mode.strategy ∈ {toggle, custom}`). Keep the **existence** test, not a strategy read: `src/components/atoms/` is `.gitkeep`-only in `template/`, so on a `strategy: none`/`system` app no `ThemeToggle.tsx` was ever authored and an unconditional import fails `tsc --noEmit`. Place it in the shell's trailing actions area (right of the nav, near any user/account affordance) — a persistent app-level control, not a page action. Do **not** author the component here; it is scaffold-authored and shared (`app-shell-spec.md`) — import it.
     - **Brand logo.** `<img src="<brand_logo.logo_src>" alt="<app name> logo" />` in the shell's leading brand region, **iff** `prototypes/.scaffold.json` has `brand_logo != null` (equivalently `prototypes/public/brand/logo.*` exists). The app title is acceptable alongside or as fallback text.
     - Both are **UI-only** — no `data-src`/`data-prop` (same exemption as search/sort/pagination). Both belong to the **application shell**, never the scaffold-authored `PrototypeChrome` review harness (PI-08): the consultant answering *"a button in the UI"* specified product behaviour, and the harness is explicitly not product.
     - **The only fallback** is a prototype that composes **no** shell component on any route (every surface renders bare page content). Then the mode stays reachable only from the landing page and no logo is rendered. Note this fallback says what to *render*; it is **not** an exemption from the gate — such a prototype still fails the per-route assertion, deliberately, because the reviewer has no colour-mode control inside the app. If you find yourself in it, prefer authoring a minimal shell. A `strategy` of `none`/`system` needs no control at all (no `ThemeToggle.tsx` exists to import, and the gate is inert); a null `brand_logo` is a valid neutral outcome.
     - **This obligation is not driver-only.** A `templates/*Shell` may be authored by a per-surface **sub-agent** (`templates/**` is in its `owned_files` space). `step-sub-render-surface.md` rule 1b binds it identically — a shell is a shell whoever writes it.
     - This is **gate-backed, not discipline-backed**: `e2e/theme-modes.smoke.spec.ts` asserts `[data-slot="colour-mode-toggle"]` is visible on **every** registered prototype route (`framework/skills/verify-prototype-build.md`), and `step-07-handback.md` greps the shell components for `ThemeToggle`.

     > **[RETIRED 2026-07-28] the slot-existence precondition.** Until 2026-07-28 both bullets above were gated on the wrapping layout *having* a header/actions slot ("When this per-prototype `layout.tsx` has a header/actions slot …"), with an explicit *"render nothing"* escape when it did not. For the toggle that precondition was **unsatisfiable by construction**: neither app-shell catalogue pattern (`framework/assets/pattern-catalogue/layouts/app-shell-with-{sidebar,topnav}.md`) declares an `actions` or `header` slot — their `required-slots` are `brand`, `primary-nav`, `main-content`, `user-menu` — so the antecedent could only ever be vacuously false. A real run read the rule, evaluated it, complied, and shipped a `strategy: toggle` prototype with no in-app colour-mode control on any route. Both bullets were **additionally** gated on a per-prototype `layout.tsx` being authored at all, which a shell composed per page (`templates/AppShellSidebar` — a first-class T1 component per `shared-component-conventions.md §7.2`) never is. Replaced by the unconditional obligation above plus the two mechanical gates it names. Do **not** reintroduce a slot or topology test.
3. **Compose** each **driver-owned** route by importing + arranging the surface's components (created or reused). Wire, exactly as the standalone sub-agents do for their own pages:
   - store usage (`useXStore`) for data display + mutation (PI-02);
   - `activeRole` from the chrome store on multi-role surfaces, varying visible components/actions per spec §6.5 RBAC (PI-05);
   - navigation per the spec's §6 model (links to `route_map` targets, command-palette entry, breadcrumbs) within the shared chrome;
   - `data-testid="primary-cta"` on the surface's primary action (verify-skill smoke contract); the chrome already carries `data-testid="proto-chrome"`.
4. **Route metadata:** set each driver-owned route's `<title>`/metadata to the prototype name.
5. Bind every data element on driver-owned routes with `data-prop="Entity.Field"` (closed set) — re-assert anti-fabrication at composition time.
5b. **Copy voice.** User-facing copy the driver authors on its routes — fold confirmation dialogs, wizard-step messages, toasts, error/empty-state text — is phrased in the spec-§3 `app_character` voice per its per-surface guidance, exactly as `step-sub-render-surface.md` rule 5b binds the sub-agents (`null` → neutral professional; tone only, never structure/labels/bindings).
6. **No per-write verify on routes.** Route files (and the per-prototype `layout.tsx`) are compile-covered — `tsc --noEmit` + the Playwright smoke gate (`step-06`) catch a bad write as a localized error the bounded-retry loop diagnoses by file path. Do **not** run `verify-artifact-write.md` on them (the option-08 compile-covered exception — see `CLAUDE.md > Constraints`).

## Anti-patterns (this step)

- **Do not treat "the shell has no header slot" as licence to omit the colour-mode toggle or the brand logo — author the region.** The catalogue patterns declare no such slot, so a slot test can only ever fail. The obligation is on the wrapping component, not on its declared slots.
- Do not satisfy the toggle obligation by passing `<ThemeToggle />` in as a page-level prop, or by relying on the landing page or `PrototypeChrome`. The first lets one composer drop it; the latter two put it outside the application under design (PI-08).
- Do not author `ThemeToggle` here — it is scaffold-authored and shared; two toggles would fight over the same `<html>` class (`prototype-generator.md > Anti-Patterns`).

Proceed to `step-06-verify-build.md`.
