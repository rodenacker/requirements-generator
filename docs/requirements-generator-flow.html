Requirements Generator — System Flowchart

How the slash commands fit together. Every engagement passes through three required steps: drop the client's material into documentation/, run /requirements to turn it into a spec, and run /export-application to hand that spec over for development. Everything else is optional — commands that check or deepen the inputs and the spec (reviews, analyses, amendments), and commands that produce extra deliverables (a PRD, a design system, wireframes, a clickable prototype). §1 shows six typical paths through them. /start lists every command and launches the one you pick. Click any box in §1 to expand its description below.

§2Reviews vs Analyses — purpose at a glance

Both optional pipeline families lens the same source material (raw documentation/ or merged requirements.md), but they produce categorically different outputs and demand different consultant actions.

Reviews

Critique — what is wrong with the source

Purpose
Surface defects, gaps, ambiguities, contradictions, completeness holes, and risks in the source material.
Output shape
A punch-list of findings — never an auto-patch. The artefact is something the consultant reads and acts on, not a positive contract for downstream tools.
Consultant action
Manual edits to documentation/ files (for /review-inputs) or to requirements.md (for /review-requirement). Some findings also generate follow-up elicitation questions for the client.
Pick when
You suspect the source is incomplete, ambiguous, or weak, and you want a structured list of specifically what to fix before drafting or designing further.
Examples
adversarial · completeness-review · ambiguity-review · first-principles · ten-ba-questions · ten-ux-questions · user-stories · gap-analysis · requirements-quality · requirements-traceability

Analyses

Transform — make implicit structure explicit

Purpose
Derive a structural model (objects, jobs, journeys, tasks, themes, state lifecycles, …) from the source so downstream design phases can key off an explicit contract instead of improvising.
Output shape
A positive artefact — object map, theme map, task tree, journey card, state diagram, opportunity-solution tree — that another pipeline can consume as input.
Consultant action
Choose Accept & use to write a compact re-ingestion extract into documentation/ for the next /requirements pass (for /analyse-inputs), or for /analyse-requirement — select it as an input to /wireframe.
Pick when
You want to enrich the source with a structural lens (motivation, object model, process flow, sentiment journey) before drafting or designing — and you want that lens to flow forward as a positive contract.
Examples
ooux · jtbd · journey-mapping · task-analysis · opportunity-solution-trees · state-diagram · data-model · use-cases · thematic-analysis · affinity-mapping · mvp-slicing · crud-coverage · decision-tables · faceted-classification · glossary · user-goal-analysis · business-context-definition

§3How outputs flow back into inputs

Pipeline outputs are not auto-piped. The consultant manually shuttles relevant pieces between runs — every cross-pipeline transfer is an explicit decision with a paper trail.

The handoff patterns

FromWhat the consultant does with the output
/generate-prd Copy strategic content (success metrics, MVP phasing, hypotheses) into documentation/ before running /requirements.
/analyse-inputs · any methodology At the end of each analysis choose Accept & use: it writes a compact Markdown re-ingestion extract (documentation/<method>.analysis.md) that /requirements reads on its next run. Plain Accept keeps the analysis for reading only.
/review-inputs · any methodology Read the punch-list and manually edit the source files in documentation/ — add missing context, resolve ambiguity, surface stakeholder voices. Then re-run /requirements against the improved corpus.
/review-requirement · any methodology Read the punch-list and manually edit generated-docs/requirements/requirements.md to address defects — or re-run /requirements with corrective input. The review never auto-patches the spec.
/resolve-review The assisted alternative to hand-editing after a review: pick an existing review artefact (generated-docs/review-inputs/ or generated-docs/review-requirements/), select the findings to act on, and resolve each one interactively — every AI-inferred resolution is confirmed by an explicit affirmative, either per finding or in one go via an explicit Accept all remaining as drafted choice (nothing is silently assumed). The approved resolutions are written as a new dated document into documentation/ (never overwriting an existing file), ready for the next /requirements run. Review-requirements-sourced runs can additionally (opt-in) cache the same resolutions as a transient Amendments section in requirements.md until the next re-merge folds them in.
Select relevant analyses (OOUX object map, user-journeys, task-flows, trade-off-dimension matrix) as supporting inputs when you run /wireframe (Stage 1b — completed analyses are read sidecar-first) or /prototype (basis B of its A–E input selection), so the produced screens and prototype reflect the lensed structure. They also remain reference reading you use to set scope and trade-off-dimension positions.

/ingest-stadium

Stadium 6 app → citation-ready input assets
Inputs
A Stadium 6 application dropped in documentation/ — a deployed app folder (administration.db + App_Data/Updates/*.sapz + ClientApp/) or a one-line *.stadium pointer naming its path. Runs a bundled, standard-library-only Python extractor.
When to use
First, whenever the client's material is a Stadium low-code app rather than (or alongside) documents. Extraction happens once per app — a process-once ledger skips an already-ingested app unless you deliberately re-ingest via the prompt, so your hand-edits to the assets are never silently overwritten.
Delivers
documentation/<AppName>.stadium-assets/ — thirteen lean, citation-ready assets (eleven deterministic category files: overview, data model, data sources, business rules, access control, surfaces, user tasks, navigation, glossary, design signals, modules; plus two advisory [AI-SUGGESTED] ones: task flows, quality signals). A forensic model.json lands under framework/state/ and is never manifested.
How to use
Nothing further — the assets are ordinary Native-text inputs. The next /requirements (or /generate-prd / /analyse-inputs / /review-inputs) run enumerates them automatically; those commands exclude the raw app folder and nudge you here if they spot an un-ingested app.

documentation/

The client's material — not a command, a folder
Inputs
Whatever the client hands over: briefs, decks, screenshots, spreadsheets, PDFs, diagrams. Text (.md, .txt, .yml, .yaml, .xml) and images (.png, .jpg, .jpeg, .gif, .webp) are read directly; Office and PDF (.docx, .xlsx, .pptx, .pdf) are converted first; diagrams (.drawio, .svg, .vsdx) are rendered and described. Anything else is logged so it doesn't slip through silently.
When to use
Always, first — after /ingest-stadium if the client gave you a Stadium 6 app. Add more files at any point; the next run of an input command picks them up.
Delivers
Nothing by itself — it is the drop zone that /requirements, /generate-prd, /analyse-inputs and /review-inputs read. The files are yours: the framework never modifies or deletes them.
How to use
Drop the files in, then run /requirements (or any of the optional input commands first). Outputs from /resolve-review and /amend-requirements land here as new dated files, and you can copy PRD or input-analysis content in by hand — see §3.
/review-inputs Optional · pre-requirements · 6 methodologies
↑ Back to paths

Critique the raw documentation/ corpus — missing context, ambiguity, contradiction, stakeholder-voice gaps. Output is a punch-list you act on by hand-editing files in documentation/ before running /requirements.

adversarial

BMAD six-dimension critique
Inputs
Every file in documentation/ via source-manifest.json. Treats the corpus as the stakeholder voice, not evidence-of-elicitation.
When to use
Before /requirements when you suspect the input set is uneven — coverage holes, mixed first- / second-hand voices, sources contradicting each other.
Delivers
generated-docs/review-inputs/ADVERSARIAL/adversarial-review.html — six-dimension findings (stakeholder coverage, workflow coverage, ambiguity, cross-source conflict, quantitative signal, scope signal) with corpus-handling recommendations.
How to use
Hand-edit the source files in documentation/ to address each finding (add context, reconcile conflict, label second-hand voices), then re-run /requirements.

completeness-review

BA-canon sweep
Inputs
Every file in documentation/ via source-manifest.json. Measures against the BA literature canon (IEEE 29148, Volere, BABOK, Wiegers, INCOSE, ISO 25010) across ten coverage dimensions.
When to use
Pick this when you need a broad, authority-grounded gap punch-list to drive client follow-up elicitation. Complementary to gap-analysis.
Delivers
generated-docs/review-inputs/COMPLETENESS-REVIEW/completeness-review.html — disposition-classified findings (Needs-Clarification / Standard-Rule-Applies / Out-of-Scope) plus per-source elicitation questions.
How to use
Use the elicitation questions to chase the client; once you receive answers, add them as new files under documentation/ and re-run /requirements.

ambiguity-review

Berry/Kamsties + Femmer taxonomy
Inputs
Every file in documentation/ via source-manifest.json.
When to use
When the input set reads "soft" — vague verbs, weak modals, optional language, undefined pronouns — and you want to nail down each ambiguity before the drafter inherits it.
Delivers
generated-docs/review-inputs/AMBIGUITY-REVIEW/ambiguity-review.html — every lexical / syntactic / referential / vague / subjective / weak-verb / optionality finding with a ready-to-paste stakeholder elicitation question.
How to use
Run the questions past the client; capture answers in documentation/ (or rewrite the ambiguous source if you have the authority) and re-run /requirements.

gap-analysis

Template-bijection delta
Inputs
Every file in documentation/ via source-manifest.json. Measures against this project's drafter template — not the BA canon.
When to use
When you want a visual, drafter-aligned gap map with pre-drafted shall-form candidate requirements. Complementary to completeness-review.
Delivers
generated-docs/review-inputs/GAP-ANALYSIS/gap-analysis.html — inline-SVG coverage heatmap, gap-matrix table by dimension × MoSCoW. Every Must/Should gap ships a shall-form Candidate Requirement.
How to use
Copy gap-analysis.html directly into documentation/ and re-run /requirements — the drafter cites it via its filename and absorbs the candidate requirements. Edit any rows you reject before re-ingestion.

ten-ba-questions

Top-10 BA gaps in the corpus
Inputs
Every file in documentation/ via source-manifest.json.
When to use
Before /requirements when you want the most consequential business-analysis gaps named rather than an exhaustive coverage audit — pick completeness-review or gap-analysis when you want every gap mapped.
Delivers
generated-docs/review-inputs/TEN-BA-QUESTIONS/ten-ba-questions-review.html — the ten most pressing stakeholder questions the gathered material leaves unanswered, ranked by business impact across eight BA gap categories, each sourced to an input file or marked absent-from-corpus.
How to use
Take the ten questions to your stakeholders and fold the answers into documentation/ before re-running /requirements — or feed the artefact to /resolve-review to turn the answers into an approved input document.

ten-ux-questions

Top-10 UX gaps in the corpus
Inputs
Every file in documentation/ via source-manifest.json.
When to use
Before /requirements when you want the most consequential UX-discovery gaps named — its sibling ten-ba-questions covers the business-analysis gaps (scope, rules, data ownership); pick completeness-review or gap-analysis when you want every gap mapped.
Delivers
generated-docs/review-inputs/TEN-UX-QUESTIONS/ten-ux-questions-review.html — the ten most pressing design questions the material leaves unanswered, ranked by design impact across eight UX gap categories (users & segmentation, context of use, goals & success signals, task flows & decision points, decision-supporting data, errors & recovery, collaboration, trust & audit).
How to use
Take the ten questions to stakeholders and users and fold the answers into documentation/ before re-running /requirements — or feed the artefact to /resolve-review to turn the answers into an approved input document.
/analyse-inputs Optional · pre-requirements · 11 methodologies
↑ Back to paths

Transform raw inputs into structured models (theme maps, task trees, object models, journeys). Every analyser ships a re-ingestion block that survives copy-into-documentation/ and feeds the drafter on the next /requirements run.

task-analysis

Hierarchical Task Analysis
Inputs
Every file in documentation/ via source-manifest.json.
When to use
When the inputs describe a goal-decomposition workflow — multi-step tasks with branches, iterations, and information requirements — and you want a numbered tree the drafter can ladder against.
Delivers
generated-docs/analyse-inputs/TASK-ANALYSIS/task-analysis.html — numbered goal / sub-goal / operation tree with mandatory Plans (sequence / selection / iteration / concurrent / discretionary) and per-terminal data-noun annotations. Embedded YAML structured tree.
How to use
Choose Accept & use at the end of the run: it writes the re-ingestion extract into documentation/; the drafter's gap-pass treats the embedded YAML tree as a bijection target — Plans seed acceptance-criteria branches, information requirements hint at §7 Data entities.

thematic-analysis

Braun & Clarke six-phase
Inputs
Every file in documentation/ via source-manifest.json.
When to use
When the inputs are heavy on qualitative material (interview notes, open-ended survey responses, stakeholder narratives) and you want to surface latent patterns before drafting.
Delivers
generated-docs/analyse-inputs/THEMATIC-ANALYSIS/thematic-analysis.html — codes, themes, theme-map (Mermaid), and a Candidate-Requirements bridge linking each theme to draftable scope.
How to use
Choose Accept & use at the end of the run: it writes the re-ingestion extract into documentation/; the drafter picks the candidate-requirement bridge up like any other source.

opportunity-solution-trees

Teresa Torres 2016 (forward discovery)
Inputs
Every file in documentation/ via source-manifest.json.
When to use
When the inputs name a desired outcome and you want to ladder it down through opportunities and solutions before the drafter commits to feature scope.
Delivers
generated-docs/analyse-inputs/OPPORTUNITY-SOLUTION-TREES/opportunity-solution-tree.html — four-layer discovery tree (Outcome → Opportunities → Solutions → Assumption-tests) with a Candidate-Requirements bridge.
How to use
Choose Accept & use at the end of the run: it writes the re-ingestion extract into documentation/; the drafter consumes the bridge section to seed scope. Use the assumption-tests to drive validation work in parallel.

journey-mapping

NN/G + Kalbach current-state journey
Inputs
Every file in documentation/ via source-manifest.json.
When to use
When the inputs describe an end-to-end user experience (one or more personas) and you need a concrete backbone for §5 task flows, §6 integration constraints, §4 NFRs, user stories, and priorities.
Delivers
generated-docs/analyse-inputs/JOURNEY-MAPPING/journey-mapping.html — one journey card per persona with phases, steps, touchpoints, channels, thoughts, emotion-curve SVG, pain-points, opportunities, moments of truth.
How to use
Choose Accept & use at the end of the run: it writes the re-ingestion extract into documentation/; the extract keeps the [SRC: <filename>] citations, so the drafter inherits the audit trail.

jtbd

Christensen-Moesta + Ulwick
Inputs
Every file in documentation/ via source-manifest.json.
When to use
When you want the requirements to anchor on user motivation rather than features — "when X, I want Y, so I can Z" — and you have raw inputs that imply jobs without naming them.
Delivers
generated-docs/analyse-inputs/JTBD/jtbd-job-map.html — canonical statements, four forces (push / pull / anxiety / habit), 5×5 Ulwick opportunity matrix.
How to use
Choose Accept & use at the end of the run: it writes the re-ingestion extract into documentation/; the drafter cites jobs as positive scope and forces as design-influence context.

ooux

Sophia Prater ORCA
Inputs
Every file in documentation/ via source-manifest.json. Synonym merge across sources is the load-bearing Round 2.
When to use
When the inputs imply a domain object model (entities, relationships, CTAs) and you want it canonicalised — with conflicting names merged and provenance preserved — before the drafter commits to §7 Data.
Delivers
generated-docs/analyse-inputs/OOUX/ooux-object-map.html — Mermaid erDiagram, OOUX sticky-note column-board, relationship matrix, and an embedded JSON object-map body block (load-bearing for drafter re-ingestion).
How to use
Choose Accept & use at the end of the run: it writes the re-ingestion extract into documentation/; the extract carries the full object model, so the drafter consumes it in one shot.

swim-lane-process-mapping

Rummler-Brache + Disconnect Analysis
Inputs
Every file in documentation/ via source-manifest.json.
When to use
When the inputs describe multi-actor processes with handoffs (the "white space" between functional silos) and you want every lane-to-lane handoff classified — clean or one of four disconnect types.
Delivers
generated-docs/analyse-inputs/SWIM-LANE-PROCESS-MAPPING/swim-lane-process-mapping.html — Mermaid flowchart TD per process with subgraph lanes, Actor inventory, Disconnect Register, embedded YAML model.
How to use
Choose Accept & use at the end of the run: it writes the re-ingestion extract into documentation/; the YAML model becomes a bijection target — processes → §5 task flows, handoffs → §6 integrations, decisions → acceptance-criteria branches, data-stores → §7 entities.

affinity-mapping

Kawakita KJ + Beyer/Holtzblatt
Inputs
Every file in documentation/ via source-manifest.json.
When to use
When the inputs are a dense pile of atomic claims (interview snippets, sticky-notes, observations) and you want them clustered bottom-up into 4–8 super-themes without imposing a prior frame.
Delivers
generated-docs/analyse-inputs/AFFINITY-MAPPING/affinity-map.html — Mermaid mindmap, cluster cards with stable/drifted confidence chips (Jaccard between two anti-anchoring passes), orphans table, optional tension flowchart, embedded JSON hierarchy.
How to use
Choose Accept & use at the end of the run: it writes the re-ingestion extract into documentation/; super-theme insight statements feed §1 vision anchors, clusters seed §5 task-flow groupings and acceptance-criteria threads, orphans feed §10 out-of-scope candidates, tensions feed trade-off-aware criteria.

glossary

Ubiquitous-language vocabulary
Inputs
Every file in documentation/ via source-manifest.json. (Distinct from the same-named /analyse-requirement method, which reads requirements.md.)
When to use
When you want one agreed vocabulary for the system before drafting — significant terms surfaced, classified domain vs application, defined from the inputs, and rated for how settled each shared understanding is.
Delivers
generated-docs/analyse-inputs/GLOSSARY/glossary.html — per-term cards with domain/application + 0–4 maturity badges and cited definitions, plus fenced proposed definitions / canonical resolutions wherever a term is left undefined, weak, synonymous, or conflicting.
How to use
Re-drop into documentation/ so /requirements adopts the agreed terms as canonical vocabulary; the blocking proposals reach the resolver as questions you confirm before they anchor requirements.

user-goal-analysis

Actor & end-user goals (GORE)
Inputs
Every file in documentation/ via source-manifest.json.
When to use
When you want the actor and end-user goals behind the request made explicit — both the goals the inputs state and the ones they imply. The actor-goal complement to business-context-definition.
Delivers
generated-docs/analyse-inputs/USER-GOAL-ANALYSIS/user-goal-analysis.html — a goal register grouped by goal type, an AND/OR refinement tree, an actor map, and a conflicts table; inferred goals flagged for confirmation.
How to use
Re-drop into documentation/ so explicit goals seed §4 user stories and inferred goals reach the resolver as questions you confirm before they become requirements.

business-context-definition

Enterprise motivation (BMM + BABOK)
Inputs
Every file in documentation/ via source-manifest.json.
When to use
When you need the enterprise motivation behind the request — the business problems, needs, and goals — rather than the individual actor goals user-goal-analysis covers. Run the two side-by-side for two clean, non-overlapping registers.
Delivers
generated-docs/analyse-inputs/BUSINESS-CONTEXT-DEFINITION/business-context-definition.html — a report linking business problem → need → goal → problem-statement in one causal chain; inferred items flagged for confirmation.
How to use
Re-drop into documentation/ so the causal chain seeds strategic framing and requirement traceability; run user-goal-analysis alongside it for actor-level goals.

/design-system

Brand token set
Inputs

/resolve-review

Review findings → approved input document
Inputs
One existing review artefact, picked from disk — any generated-docs/review-inputs/<METHOD>/ or generated-docs/review-requirements/<METHOD>/ output. Run a review first.
When to use
After a review, when you want its findings acted on rather than just listed — the assisted alternative to hand-editing documentation/ files or requirements.md. You select which findings to address and resolve each one in turn; every AI-inferred resolution is confirmed by an explicit affirmative — per finding, or in one go via an explicit Accept all remaining as drafted choice — before it is recorded.
Delivers
One new dated resolutions document under documentation/ per run — existing input files are never modified or overwritten. Each resolution is origin-marked (consultant-stated vs AI-inferred-and-confirmed) and carries a Supersedes line so cross-source-conflict detection stays honest. On review-requirements-sourced runs you can additionally opt in to a transient Amendments (pending re-merge) section cached inside requirements.md for immediate downstream use.
How to use
Re-run /requirements — the resolutions document is picked up like any other input file and your decisions are folded into the regenerated spec (which also clears the transient Amendments cache). One run resolves one review; re-invoke for another.

/amend-requirements

Consultant-stated changes → approved amendments
Inputs
A finished generated-docs/requirements/requirements.md plus the changes you state in your own words — name a section or requirement ID (§6.3, F-07) or just describe what you want different.
When to use
The spec is written and you already know what to change — no review involved. Reachable directly, or as the amend option when you re-run /requirements on a finished spec.
Delivers
A new documentation/amendments-<date>.md — the durable record, folded into the spec body with citations by the next /requirements run — and a transient ## Amendments (pending re-merge) section inside requirements.md, so /wireframe, /prototype, the analyses and /export-application honour the change immediately. Nothing existing in documentation/ is overwritten and no other line of the spec is touched.
How to use
A specific change is recorded as you stated it; a change that is only a direction ("tighten up approvals on rate changes") comes back as two or three concrete alternatives with their consequences, and you pick one. You are also told what the change affects — data properties the wireframes bind to, the scope boundary, and which wireframes or exports were built against the older spec.

/export-application

Application-audience re-projection of the spec
Inputs
generated-docs/requirements/requirements.md — sole content input, exported as it exists at that moment, amendments included. Pending amendments are first folded into the export's copy of the body, with every edit listed in fold-report.md for you to check at the gate. Apart from that fold, nothing is invented at export time — the only export-supplied wording is a small fixed set of replacements. requirements.md is never changed.
When to use
Once the requirements have settled — after the analyses, reviews, wireframes, and manual refinements have shaped the spec into what you actually want built — and a dev team outside this workspace needs the build-ready version.
Delivers
generated-docs/export-application/requirements-application.md (plus fold-report.md when amendments were folded; an amendment whose anchor can't be found stops the run before any write) — amendments folded into the body, prototype-only scaffolding stripped (the prototype-invariants appendix and the framework-internal target-mode table), fixture references rebased to backend-contract pointers, the prototype-scoping preamble dropped from the guidance sections, and a provenance block stamped in with a sha256 fingerprint of the exact source version, so a re-run can tell you whether the export is stale. Anything that can't be cleanly re-projected — a prototype-flavoured phrase inside a cited requirement, say — is left exactly as written and flagged in the provenance block and under the affected section, rather than quietly reworded. Self-describing for external readers via a citation legend.
How to use
Hand it over together with generated-docs/requirements/draft-claims.ndjson (the verbatim source quotes behind the citation tags). Re-running after the spec changes offers a one-click regenerate; the prior export is checkpointed to git first.
